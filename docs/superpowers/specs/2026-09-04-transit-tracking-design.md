# 在途貨物追蹤號整合 — 設計

日期：2026-09-04
狀態：階段一已核准，階段二待 API key

## 背景

台灣倉出貨到海外倉時，目前有兩套並存的機制：

- **手動在途**：一個 EAN 一個數字，存在 `Shared` 分頁。**分不了批**，同一產品同時有多批在海上就沒辦法分開管理，而且不會自動記帳。
- **在途貨物追蹤（Transits）**：一批一列，出發時自動從來源倉扣掉、到貨時自動加到目的倉。分批本來就支援。

痛點是無法得知每批貨走到哪裡，到貨也得靠人記得回來按確認。

出貨方式**海運併櫃與快遞都有**：快遞有成熟的追蹤 API，海運貨代通常沒有。

## 目標

1. 每批在途可記錄追蹤號，一眼看出哪批到哪了
2. 貨態顯示已送達時，把該批推到眼前等待確認
3. 同一產品的多批貨各自獨立管理

## 非目標

- **不自動寫入庫存。** 快遞的「已送達」只代表送到倉庫門口，不等於海外倉點收入帳。
  少件、破損、延遲上架都會讓帳面出現不存在的貨，事後很難回頭修。
  入庫一律由人確認，系統只負責把該處理的推到眼前。
- 不做 webhook。一次只有幾批貨在海上，每天輪詢幾筆的成本微不足道，
  而 webhook 需要對外開放匿名的 `doPost` 端點，多了攻擊面又難除錯。

## 資料結構

`Transits` 分頁尾端加四欄（沿用「新欄位加尾端」的慣例，既有讀取邏輯按名稱查找不受影響）：

| 欄位 | 用途 |
|---|---|
| `tracking_no` | 追蹤號，可留空（海運貨代沒有就不填） |
| `carrier` | 業者代碼，留空則由 API 自動辨識 |
| `tracking_status` | 最近一次抓到的貨態原文 |
| `tracking_checked_at` | 最後查詢時間，用來判斷輪詢是否正常 |

## 狀態流程

```
TRANSIT ──貨態=已送達──> ARRIVING（待確認到貨）──人工確認──> ARRIVED
                                                    │
                                   可於此處修改箱數（少件、破損）
```

階段一由人手動標記 `ARRIVING`；階段二改由輪詢自動標記。
實際入庫仍走既有的 `confirmArrival()`。

## 階段一（本次實作）

- `Transits` 加四個欄位
- 新增在途時可填追蹤號與業者
- 在途清單顯示追蹤號（可點，跳到業者查詢頁）與貨態
- `ARRIVING` 狀態：可手動標記，該批排在最上面並標色
- 確認到貨流程支援從 `ARRIVING` 轉 `ARRIVED`

不需要任何外部服務，立即可用。

## 階段二（待 API key）

- 每日排程輪詢 `status=TRANSIT` 且有 `tracking_no` 的批次
- 抓取包在單一函式 `fetchTrackingStatus_(trackingNo, carrier)`，換供應商只改這一支
- 貨態為已送達時自動轉 `ARRIVING`
- 查詢失敗寫進 `tracking_status`，連續多天失敗以 `notifySyncFailure_()` 通知
- **抓不到貨態絕不影響既有資料**

候選供應商（2026-09-04 查證）：

- **17TRACK** — 3400+ 業者，header 帶 `17token` 認證，新帳號一次性 200 個免費單號
  （2026/1 起改為一次性配額，非每月）。文件未明載海運貨代支援程度，需實測。
- **AfterShip** — 文件完整度較高，之後要換不難。

## 風險

| 風險 | 處置 |
|---|---|
| 快遞「已送達」≠ 倉庫入帳 | 絕不自動寫庫存，一律人工確認 |
| 海運貨代查不到 | 追蹤號留空即可，該批照常顯示、只是貨態空白 |
| 供應商配額用盡或改版 | 抓取集中在單一函式，可換供應商；失敗不影響既有資料 |
